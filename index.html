Zero to production AI agents in one day on AWS Bedrock AgentCore.

A Dog Days of DevOps Lightning talk by Evan Niedojadlo

One day. Production. For real.

In February I built a multi-agent platform on AWS Bedrock AgentCore with the Strands Agents SDK. First working agent to production: in a day. Then months of iterating while it ran.

This talk is the recipe, and the guardrails I only learned by getting burned.

Hire robots, not bots

The core design decision: every agent is an AI employee, not an integration.

  • Its own company email and its own Slack account
  • Its own database user, Jira/Confluence account, and secrets path
  • A "soul": a wiki page it reads at boot that defines its personality and job

Payoff: every query, comment, and commit is attributable and every credential is independently rotatable. Security people sleep at night.

The stack (small on purpose)

  • AgentCore Runtime: serverless containers, direct code deploy, versioned rollbacks
  • Strands SDK: @tool functions, model switching, MCP, memory
  • Python 3.11 + uv + ruff; Claude on Bedrock by default, ~11 models swappable per session
  • Built-in Code Interpreter sandbox + managed Browser

No Kubernetes to babysit. No GPU bill. The platform is boring so the agents can be interesting.

Tools: three scoops, one cone

  • Scoop 1: framework tools (code interpreter, browser)
  • Scoop 2: a shared org toolbox: data warehouse, Jira, Slack, GitHub, wiki, dashboards… ~40 modules
  • Scoop 3: agent-specific tools on top

Every agent gets every tool by default; access control is a denylist in config, never a forked copy of the code. CI fails any PR where an agent's tool bundle drifts from the shared library.

House rule: no tool ships without a wiki page, and that index is literally what agents read when you ask "what can you do?"

Slack: they show up as people

Two Lambdas per agent: a dispatcher (verifies, drops an 👀 ack) and an async worker that calls the runtime and replies with the agent's user token, so it appears as a person, not an app.

Slack is the source of truth: the worker re-hydrates the whole thread on every invoke. No sticky sessions, no state to lose.

Learned the hard way: require @-mentions (stops multi-agent pile-ons), convert Markdown tables to code blocks, and invalidate sessions on every deploy.

Let workflows graduate

Rule: every step that can be code, is code. The LLM only handles steps that genuinely need judgment. Each workflow has three lives:

  • Agentic: runs in the agent, LLM makes the judgment calls
  • Ejected in-process: same Python, deterministic fallbacks, used for tests
  • Ejected to n8n: one command compiles it to workflow JSON and pushes it to run on cron at zero AI cost

Prototype with reasoning. Ship as plain code. Your token bill melts instead of your budget.

The code factory (yes, really)

The agents extend themselves. One Slack message →

  • agent reads existing patterns from the repo
  • drafts the tool + pytest, loops in the sandbox until green
  • opens a PR to trunk → auto-merge on green CI → deploy
  • live in ~2.5 minutes, no human in the path

26 of 170 merged PRs were authored by the agents. Trunk-based, one environment, no staging soak; the trust boundary is CI, plus a post-deploy smoke test, plus a one-line version rollback.

Popsicle stick wisdom

  • Identity per agent. Attribution and rotation are the whole security story.
  • Rent the runtime. Serverless agents = production in days, not quarters.
  • Code > tokens. Graduate proven workflows out of the LLM.
  • CI is the trust boundary. That's what makes self-modifying agents safe enough.
  • Write the docs. Your agents are reading them.
